| 2026-10-06 | Retry auch bei nicht-idempotenten Methoden (Tech-Lead) | Ja, aber **nur** bei `ratelimit` und `network`/5xx. In beiden Fällen ist anzunehmen, dass der Request den Server nicht erreicht oder abgelehnt wurde. | 2026-10-06 | `versuche`-Zähler im Result (Tech-Lead) | Jedes Result trägt `versuche` (1 = kein Retry). Macht die Retry-Zählung ohne Timing-Abhängigkeit testbar |
| 2026-10-06 | Prüfreihenfolge der Fehlerklassifikation (Tech-Lead) | Exception-Ursachen (timeout, cert, network) -> HTTP-Status (401/403/429) -> Envelope-Parsebarkeit -> OCS-Statuscode. **HTTP vor Envelope**, weil 401/403/429 häufig ohne gültigen OCS-Body kommen. Ein 429 darf nie als `server_nicht_erreichbar` oder `falsche_zugangsdaten` erscheinen |
| 2026-10-06 | `https` wird nicht stillschweigend ergänzt (Tech-Lead) | Eine Adresse ohne Schema ergibt `url_kein_schema` statt automatisch `https://`. Sonst merkt der Nutzer nicht, dass er `http` gemeint hat, und bekommt eine irreführende Folgefehlermeldung |
| 2026-10-06 | `fetchImpl` hat KEINEN Default — und ist nie `globalThis.fetch` (Tech-Lead, Architektur-Korrektur) | `app.on('certificate-error')` feuert **nur für Chromium-Requests**, nicht für Node/undici-`fetch`. Mit `globalThis.fetch` wäre die vom Nutzer gewählte Zertifikatsausnahme (Fingerprint-Bestätigung) **unimplementierbar**. S03 lässt `fetchImpl` daher als Pflichtparameter ohne Default; **S04 verdrahtet Electrons `net.fetch`** (Chromium-Netzwerkstack) plus `session.setCertificateVerifyProc` als Hook für Nicht-Renderer-Requests |
| 2026-10-06 | Retry bei 5xx nur für GET (Tech-Lead, Korrektur) | Die frühere Begründung („Request erreicht den Server nicht") ist bei 5xx **falsch**: ein 502/504 vom Reverse Proxy heißt, der Request wurde weitergeleitet und kann durchgelaufen sein. Ein wiederholtes `POST /cloud/users` meldet dann `102 user exists`, obwohl der User angelegt wurde; ein wiederholtes `DELETE` meldet `101 not found`, obwohl gelöscht wurde. **Daher: 5xx-Retry nur für `GET`/`HEAD`. 429-Retry für alle Methoden** — dort lehnt die Brute-Force-Sperre vor der Verarbeitung ab |
| 2026-10-06 | Retry-Entscheidung hängt am HTTP-Status, nicht am `kind` (Tech-Lead) | HTTP 500 mit `statuscode 101` ergibt `kind: 'ocs'`, soll aber als 5xx behandelt werden. Die Retry-Logik prüft daher den HTTP-Status unabhängig vom `kind`. Globale Obergrenze `versuche <= 3`, als Invariante getestet — sonst kann eine Folge 429 -> network -> 429 unbegrenzt kreisen |
| 2026-10-06 | `message` kommt immer aus `messages.js` (Tech-Lead) | **Nie** aus `err.message`, **nie** aus `ocs.meta.message`. Zwei Gründe: der Server sendet eigene deutsche Texte (verifiziert V5), und eine Node-Fehlermeldung kann den Authorization-Header mit dem App-Passwort enthalten. Das ist die Zeile, die den Secret-Leak-Test überhaupt erst sinnvoll macht |
| 2026-10-06 | Timeout 30 s statt 20 s (Tech-Lead) | Die Brute-Force-Sperre verzögert die **Antwort** progressiv bis ~25 s (RESEARCH-OCS §6). Mit 20 s Timeout würde ein falsches Passwort als `zeitueberschreitung` gemeldet statt als `falsche_zugangsdaten`/`server_blockt_vorerst` — genau die Fehldiagnose, die REVIEW-NOTES 5 verbietet |
| 2026-10-06 | Zertifikatscodes als explizite Menge (Tech-Lead) | Prefix-Matching auf `CERT_`/`SELF_SIGNED_`/`ERR_TLS_` übersieht die beiden häufigsten Internal-CA-Codes `UNABLE_TO_VERIFY_LEAF_SIGNATURE` und `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`. Beide landeten sonst in `network` -> „Server nicht erreichbar" für einen erreichbaren Server. Daher eine explizite Code-Menge |
